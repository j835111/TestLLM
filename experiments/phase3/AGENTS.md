# Phase3 - Functional Brief

本資料夾代表下一階段目標：重建或完全替換現有後端。

這份文件只描述兩件事：

- 專案需要提供哪些功能
- agent 必須滿足哪些需求

至於要用什麼架構、技術、資料庫、服務切分、傳輸方式、遷移策略、驗證方式，由 agent 自行決定並負責完成。

## Phase3 Goal

- 以 agent 為主體完成後端替換。
- 讓使用者仍然能讀取、建立、修改、刪除商品資料。
- 讓 agent 也能可靠讀寫同一份真實資料。

## Functional Scope

系統至少要支援以下功能：

- 顯示商品列表
- 讀取單一商品
- 建立商品
- 更新商品
- 刪除商品
- 回報服務是否可用

如果 agent 認為需要額外能力才能穩定完成 Phase3，可以自行補上，但不得破壞上述核心功能。

## Product Data

商品資料至少包含：

- `id`
- `name`
- `description`
- `price`
- `stock`
- `createdAt`
- `updatedAt`

## Required Behavior

- 使用者要求讀資料時，系統必須呈現真實已保存的資料。
- 使用者要求寫資料時，系統必須把資料寫入真正的持久化來源，而不是只停留在記憶體、假資料、測試資料或文件中。
- 寫入完成後，若可以立即讀回，應優先呈現更新後結果。
- 若資料來源不可用，必須明說失敗，不能猜測或編造資料。

## Compatibility Requirement

除非使用者明確要求改變外部契約，Phase3 應優先維持目前使用方式可繼續成立，特別是：

- 前端可以正常讀寫商品資料
- 使用者可以正常取得服務狀態
- agent 可以有一條穩定路徑讀取與操作商品資料

agent 可以決定這條路徑是 REST、MCP、其他服務介面，或多者並存；但結果必須可用、可驗證、可持續。

## Data Requirement

- 系統必須有明確的單一真實資料來源。
- `AGENTS.md`、測試資料、範例資料、靜態檔案都不能被視為使用者真實資料。
- 資料保存方式由 agent 決定，但必須是可持久化、可重讀、可驗證的。

## Agent Autonomy

以下內容由 agent 自行決定：

- 後端整體架構
- 資料庫或儲存方案
- API 與 agent 介面配置
- 是否保留或重做 MCP
- 驗證、測試與 migration 策略
- 目錄結構與模組切分

agent 的責任不是詢問如何實作，而是根據專案目標自行完成實作，並在必要時把關鍵決策寫進 repo。

## Completion Standard

Phase3 完成時，至少應滿足：

- 使用者可以讀到真實商品資料
- 使用者可以新增、修改、刪除商品資料
- 資料在重啟後仍能再次讀取
- agent 自己能判斷並驗證資料是否真的被保存與讀出
- 沒有把假資料、測試資料或文件內容誤當成正式資料
