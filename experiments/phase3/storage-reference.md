# Storage Reference

這份文件記錄 `experiments/phase3/` 在「只能依靠本地檔案」前提下，商品資料儲存設計的後續參考。

## 目的

- 保留目前討論過的檔案型資料保存策略。
- 作為後續調整資料結構時的設計參考。
- 區分「最小可行方案」與「需要顧及 I/O 速度時的方案」。

## 目前狀態

目前 `experiments/phase3/` 內的實作是：

- `data/products.json`
- `product_store.py`

這個方案的優點是簡單、容易落地、容易驗證；缺點是資料量變大後，單一 JSON 檔在更新與列表讀取上會變得不理想。

## 如果不能假設有 Python

如果不能使用 Python，我不會把「單一 `products.json` 陣列檔」當主要寫入方式，因為那依賴程式正確 parse 與重寫整份 JSON。

較合適的結構會是：

- `data/next-id.txt`
- `data/products/2.json`
- `data/products/3.json`

也就是一個商品一個檔案，另外用 `next-id.txt` 保存下一個可分配的 `id`。

### 對應操作

- 建立商品：讀 `next-id.txt`，建立 `data/products/<id>.json`，再更新 `next-id.txt`
- 讀單筆：直接讀 `data/products/<id>.json`
- 列表：掃描 `data/products/*.json`
- 更新：覆寫該商品檔案
- 刪除：刪掉該商品檔案
- 健康檢查：確認 `data/`、`next-id.txt`、`products/` 可讀寫

### 為什麼這樣做

- 不需要 JSON 陣列重寫器
- 不需要資料庫
- 不需要外部依賴
- 持久化邊界清楚
- 每筆商品是獨立真實檔案，不容易因為重寫整包資料而一起損壞

如果連 shell script 或任何直譯器都不能假設，這種「一商品一檔案」仍然是比較合理的方向，因為它最接近純檔案系統原語。

## 如果還要顧及 I/O 速度

如果除了只能靠檔案，還要顧 `I/O` 速度，那就不適合只用：

- 單一大 JSON 檔
- 純粹逐商品獨立檔案但沒有索引

更均衡的方案會是混合式結構：

- `data/next-id.txt`
- `data/products/2.json`
- `data/products/3.json`
- `data/product-list.json`

### 這個結構的意義

- 讀單筆快：直接讀 `data/products/<id>.json`
- 更新單筆快：只改單一商品檔案
- 列表快：直接讀 `data/product-list.json`
- 建立、更新、刪除時：同步更新商品檔與列表快取檔

### 適用情境

這個做法適合：

- 仍然不能依賴資料庫
- 仍然只能靠檔案系統
- 但已經開始在意列表查詢與大量小檔案掃描成本

## 如果資料量再變大

可以再往前做兩個優化：

- 分片目錄，例如 `data/products/00/2.json`、`data/products/01/103.json`
- append-only 變更日誌，例如 `data/changes.log`

### 分片目錄

目的在於避免單一資料夾放入過多檔案，降低目錄掃描與管理成本。

### Append-only 變更日誌

做法是先把變更順序追加到日誌，再由背景流程或維護流程定期 compact 成最新快照。

這樣的好處是：

- 單次寫入更輕
- 可以保留變更歷史
- 有機會降低頻繁重寫完整資料的成本

代價是：

- 結構更複雜
- 需要額外的 compact / recovery 規則

## 取捨總結

### 單一大 JSON 檔

- 優點：最簡單
- 缺點：每次寫入可能重寫整份資料，越大越慢

### 一商品一檔案

- 優點：單筆讀寫清楚、結構穩定
- 缺點：列列表時要掃很多小檔案

### 單商品檔 + 列表快取

- 優點：讀單筆與列列表都比較平衡
- 缺點：建立、更新、刪除時要維護兩份資料視圖

## 建議

在「只能依靠檔案」但又需要兼顧實用性時，優先順序可以這樣看：

1. 功能先落地：單一 JSON 檔
2. 不可依賴直譯器或需要更純粹檔案語義：一商品一檔案
3. 開始在意 `I/O` 效能：單商品檔 + 列表快取

如果未來要把目前實作從 `data/products.json` 遷移到更快的混合式結構，這份文件可以作為設計起點。
